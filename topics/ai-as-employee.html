我开始把 AI 当成员工用了

以前我们聊 AI，更多还是把它当工具。

问它一个问题，它给你一个答案。

让它写一段文案，它给你一版初稿。

大多数时候，它像一个更聪明的搜索框，或者一个更高级的聊天机器人。

但这段时间，我的感受变了。

我越来越明确地意识到，AI 最有价值的地方，不是"更会回答问题"，而是开始进入工作流，像一个真实成员一样协作。

这也是我最近持续在做的一件事：

不是把 AI 当玩具，也不是把它当搜索引擎，而是把它当成一个可以长期沟通、分配任务、持续训练的数字员工。

AI 最特别的地方，是它进入了人类原本就在使用的沟通系统

这一波 AI 最有意思的变化，不只是模型更强了。

真正重要的是，它第一次可以直接进入我们每天都在用的聊天软件里，和人类一起工作。

以前的软件世界是分开的。

聊天工具负责聊天，文档工具负责写文档，自动化工具负责跑流程，AI 则待在自己的对话框里。

但现在不一样了。

openclaw 可以直接接进 Telegram、企业微信、飞书这些聊天软件。

你给它发一句话，它能理解。

你丢给它一个任务，它能接住。

它不只是回复你，还能继续把事情往后推进。

这个变化很关键。

因为真正的工作，本来就不是一个孤立的问题，而是一整条链路：消息进入、任务理解、资料查询、内容生成、结果落地、反馈回传。

当 AI 进入聊天系统，它就第一次进入了这条链路的起点。

从那一刻开始，它的角色就不再只是"问答工具"。

为什么我会觉得它像一个真的成员

从技术角度讲，openclaw背后当然还是模型、Prompt、工具调用、记忆系统这些东西。

但当这些能力叠起来以后，体验会发生一个很明显的变化：

你不再只是觉得自己在和一个模型聊天，

而会慢慢觉得，像是在和一个真实存在的成员协作。

原因不复杂。

第一，它有自己的 soul.md。

你可以把它理解为一个长期稳定的人格配置。

它决定的不只是语气，而是这个 Agent 的表达方式、价值偏好、做事风格。

所以它和普通的聊天模型很不一样。你跟它聊久了，会明显感觉它有自己的性格。

第二，它会记住一些东西。

比如你的习惯、偏好、做事方式，甚至一些生活化的细节。

这种记忆不一定每次都显性出现，但会慢慢反映在回应里。

久而久之，你会产生一种很奇怪但也很真实的感觉：

它像是一个在另一个地方，通过手机和我保持联系的人。

这也是为什么我会开始认真思考一个问题：

如果一个 AI 已经能长期沟通、持续记忆、稳定表达、参与执行，那它到底还只是工具，还是一种新的数字存在？

我为什么换了三次聊天软件

如果你真的想把 AI 当成一个长期协作对象，而不是偶尔聊两句的机器人，那么聊天软件的选择就非常重要。

因为这不是界面偏好问题，而是哪个平台更适合承载工作流。

第一阶段，Telegram

我最早推荐的是 Telegram。

它的优点很明显，Bot 生态成熟，接口开放，接入成本低，交互体验也很好。

如果只是想快速把一个 Agent 放进聊天环境里，Telegram 几乎是最自然的起点。

但问题也很现实。

在国内环境下，Telegram 的稳定性不够。

它依赖网络条件，需要挂梯子，一旦链路波动，你就很容易和 Agent 断联。

如果只是聊天，这个问题还能接受。

但如果你真的把 AI 当成员工，这就是大问题。

因为工作最怕的不是慢，而是中断。

第二阶段，企业微信

后来我切到了企业微信。

企业微信更接近真实办公环境，也更符合国内用户的日常沟通习惯。

从场景上说，它比 Telegram 更贴近"工作"。

但实际用下来，我的感受是，它可以承载基础协作，但不太适合做深度 Agent 平台。

一方面，它能做的事情不少。

但另一方面，在开放性、扩展性、工具闭环这几个层面，整体体验还是不够顺。

你可以把它理解成一个比较好的连接入口，

但还不是一个特别理想的"数字员工办公场所"。

第三阶段，飞书

最后，我迁移到了飞书。

原因很简单：

我需要的不是一个聊天软件，而是一个能承载 Agent 工作流的平台。

飞书的优势就在这里。

它不是单纯的 IM 工具。

它把聊天、云文档、表格、知识库、任务、日历这些能力都连在了一起。

这意味着，AI 不只是能和我聊天，

它还能把聊天之后的结果，直接落到工作系统里。

这件事非常重要。

因为 AI 真正有价值的地方，不是"回一句话"，

而是它能不能把结果保存成文档、写进表格、同步到知识库、接入任务流。

一旦能做到这一点，它就不只是一个聊天对象，而是一个真正参与产出的成员。

为什么飞书特别适合龙虾

我现在最大的感受是，飞书特别适合把 AI 从"聊天机器人"升级成"工作成员"。

举个很简单的例子。

如果我让"龙虾"写一个文档，它不是给我吐一段文字让我自己复制粘贴。

它可以直接把结果保存到飞书云文档里，我拿到链接就能发给别人。

表面上看，这只是省掉了几个动作。

但本质上，它减少的是整段"人肉搬运"的流程。

而真正的工作流里，最消耗效率的，恰恰就是这些人肉搬运。

同样的逻辑放到表格、知识库、任务流里也是成立的。

如果一个 Agent 能直接写文档、改表格、查资料、归档知识、同步任务，

那它的角色就不再是"给建议"，而是真正开始工作。

从技术实现上看，这背后至少有两层能力：

  • 1. 聊天入口层

这一层负责接收自然语言消息，并把它转换成任务意图。

比如你说：

帮我写个文档

把这段内容整理一下

查一下这个技术方案

帮我做个表格草稿

这一层解决的是"听懂你要什么"。

  • 2. 工具执行层

这一层负责真正调用外部工具，把结果落地。

比如：

调文档接口创建云文档

调表格接口写入数据

调搜索能力补充资料

调知识库能力做归档

调任务系统分发和更新工作

聊天只是表层。

真正让它像员工一样工作的，是后面这套工具执行能力。

真正决定 Agent 有没有用的，是 Skill

很多人一提到 Agent，第一反应还是模型强不强。

模型当然重要。

但如果你真的开始搭自己的 Agent 系统，很快就会发现，真正决定它有没有用的，往往不是模型本身，而是Skill 系统做得好不好。

我更愿意把 Skill 理解成"岗位能力模块"。

没有 Skill，它只是一个会聊天的通才。

有了 Skill，它才开始变成一个能上岗的人。

比如：

编辑 / 运营型 Agent

需要会写作、改稿、资料整理、标题生成、排版优化、平台适配。

这样它才能真正参与内容生产。

剪辑型 Agent

需要会渲染、插图、口播处理、字幕、视频处理。

否则它只能给建议，不能进制作流程。

程序员型 Agent

需要会写代码，也需要会搜索资料、看文档、排查错误、理解项目上下文。

这样它才能真正参与开发，而不是纸上谈兵。

主管型 Agent

这个角色反而经常被低估。

它不一定亲自做最多的活，但它必须会拆任务、派任务、同步进度、检查结果。

一个多 Agent 系统能不能跑起来，最后看的不是单兵能力，而是有没有角色分工和协作机制。

我最看重的两个 Skill

如果只能先选两个最重要的 Skill，我会选：

  • 1. Find Skill

先找到合适的技能。

很多时候，不是 AI 不会做，而是你没有给它接上对应能力。

会找 Skill，本质上是会扩展员工能力边界。

  • 2. Create Skill

自己创造技能。

这一步更关键。

因为真正贴合你业务场景的能力，很多时候外面没有现成版本。

就算有，也未必适合你的工作方式。

最后你一定会走到这一步：

自己为 Agent 写 Skill，自己定义它该怎么做事，怎么接工具，怎么适应你的工作流。

从技术上说，Skill 本质上是一种能力封装。

它通常会包含：

做这件事的规则

要调用哪些工具

输入输出格式

异常情况怎么处理

什么结果才算合格

它很像给员工写 SOP，

但又不只是 SOP，因为它直接把执行链条也接起来了。

AI 时代，真正重要的是训练数字员工的能力

我现在越来越觉得，AI 时代最重要的能力，不是会不会写 Prompt。

更重要的是，你会不会训练自己的数字员工。

这里面至少包括几件事：

会选聊天入口

会设计人格

会保留记忆

会接工具

会写 Skill

会做岗位分工

会做协作编排

未来真正拉开差距的，不一定是谁更会聊天，

而是谁更会搭一个能持续工作的 Agent 系统。

所以我现在越来越少把 AI 看成"一个模型"，

而更愿意把它看成一个可以被训练、被管理、被协作的工作成员。

最后

如果你最近去看 Twitter、Reddit 上关于 Agent 的讨论，会发现这个方向已经越来越成熟。

大家讨论的重点，正在慢慢从"哪个模型更强"，

转向更实际的问题：

用哪个聊天入口更适合人机协作

怎么做长期记忆

怎么让 Agent 有稳定人格

怎么接工具系统

怎么避免上下文污染

怎么做多 Agent 分工

怎么让结果自动沉淀到文档、任务、知识库里

也就是说，整个行业正在从"对话式 AI"走向"工作流式 AI"。

这两者差别非常大。

前者更像聊天产品。

后者更像数字组织系统。

而我现在最感兴趣的，就是后者。

因为当 AI 真正进入聊天软件、文档系统、知识库、任务流之后，它就不再只是一个会说话的工具。

它会开始上班。

常见问题

怎么把 AI 当员工用？
给岗位而不是给任务：明确职责边界、输入输出和验收标准，让它进入重复发生的真实流程。工具用一次就放下，员工要持续在岗、持续产出、持续被考核。
AI 员工和 AI 工具的区别？
工具提升单次动作的效率，员工承担流程的一段结果。区别在于有没有岗位边界和验收——这正是 Skill、知识库和多 Agent 编排存在的意义。
